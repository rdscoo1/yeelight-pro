# Codebase Concerns

> Generated by codebase mapper on 2026-03-29

## Critical

### Bug: `send_command` service passes positional args incorrectly to `gateway.send()`

- Issue: `custom_components/yeelight_pro/__init__.py` line 234 calls `await gtw.send(method, params, True)`. The `send()` signature is `send(self, method: str, wait_result: bool = True, **kwargs)`. This means `params` (a dict) is passed as `wait_result`, and `True` is an extra positional arg causing a `TypeError` at runtime.
- Files: `custom_components/yeelight_pro/__init__.py:234`, `custom_components/yeelight_pro/core/gateway.py:599`
- Impact: The `send_command` service is broken -- any call will raise a `TypeError`. This service is used for debugging and manual gateway interaction.
- Fix approach: Change to `await gtw.send(method, params=params, wait_result=True)` or `await gtw.send(method, wait_result=True, params=params)`.

### Use of `ast.literal_eval()` on user-provided input

- Issue: The `mock_incoming_message` service uses `ast.literal_eval()` as a JSON fallback to parse user-supplied message strings.
- Files: `custom_components/yeelight_pro/__init__.py:280`
- Impact: While `ast.literal_eval()` is safer than `eval()`, it still evaluates Python literal expressions from external input. In a Home Assistant context, this service is admin-only (registered via `hass.services.async_register`), but it expands the attack surface if HA access controls are misconfigured.
- Fix approach: Remove `ast.literal_eval()` fallback. Only accept valid JSON. Provide a clear error message explaining JSON format requirements.

## High

### No authentication or encryption on gateway TCP connection

- Issue: The `ProGateway` connects to the Yeelight gateway on TCP port 65443 with no TLS, no authentication, and no message signing. Any device on the LAN can send commands.
- Files: `custom_components/yeelight_pro/core/gateway.py:328` (`asyncio.open_connection(self.host, self.port)`)
- Impact: Any network-adjacent attacker can inject commands (turn on/off lights, activate scenes, control covers/climate). Messages are plain JSON over TCP with `\r\n` delimiters.
- Current mitigation: This is a limitation of the Yeelight Pro gateway hardware protocol -- the gateway itself does not support TLS. LAN network segmentation is the only mitigation.
- Recommendations: Document this security limitation prominently. Consider adding an optional IP allowlist or HMAC validation if the gateway firmware ever supports it.

### Hardcoded TCP port 65443

- Issue: The gateway port is a class-level default (`port: int = 65443`) with no way to override it via config flow or YAML configuration.
- Files: `custom_components/yeelight_pro/core/gateway.py:95`
- Impact: If Yeelight changes the port in a firmware update, or if users need to use port forwarding, there is no way to configure it without modifying source code.
- Fix approach: Add `CONF_PORT` to the config flow options schema (similar to `CONF_KEEPALIVE`), default to 65443.

### Broad `except Exception` clauses without logging in converters

- Issue: Multiple converter encode/decode methods catch bare `Exception` and silently swallow errors, returning default values without any logging.
- Files:
  - `custom_components/yeelight_pro/core/converters/base.py:96` (`BrightnessConv.decode`)
  - `custom_components/yeelight_pro/core/converters/base.py:103` (`BrightnessConv.encode`)
  - `custom_components/yeelight_pro/core/converters/base.py:123` (`ColorTempKelvin.encode`)
  - `custom_components/yeelight_pro/core/converters/base.py:143` (`ColorRgbConv.encode`)
- Impact: Malformed data from the gateway silently results in 0-value brightness/color/temp without any diagnostic trace. Makes debugging device issues very difficult.
- Fix approach: Add `_LOGGER.warning()` in each except block, or narrow exceptions to `(TypeError, ValueError)`.

## Medium

### Code duplication across entity platform modules

- Issue: Every platform module (`light.py`, `switch.py`, `sensor.py`, `cover.py`, `climate.py`, `number.py`, `button.py`, `binary_sensor.py`, `update.py`) repeats an identical boilerplate pattern: `setuper()` closure, `async_setup_entry()`, and `async_setup_platform()`. These three functions are structurally identical across all 9 platform files with only the entity class and domain varying.
- Files: All entity platform files under `custom_components/yeelight_pro/`
- Impact: Adding a new platform requires copying 15-20 lines of boilerplate. Any change to the setup pattern (e.g., error handling, logging) must be replicated across 9 files.
- Fix approach: Extract a generic `platform_setup_factory(entity_domain, entity_factory_fn)` helper that returns the three functions.

### `GroupDevice` duplicates `LightDevice` converter setup

- Issue: `GroupDevice.setup_converters()` manually repeats almost the same converter list as `LightDevice.setup_converters()` (PropBoolConv for power, DurationConv, BrightnessConv, ColorTempKelvin). The group always assumes brightness + color_temp support without checking actual group member capabilities.
- Files: `custom_components/yeelight_pro/core/device.py:733-741` vs `custom_components/yeelight_pro/core/device.py:533-546`
- Impact: Groups always expose color_temp controls even if group members are on/off-only lights. Changes to light converters must be mirrored manually.
- Fix approach: Have `GroupDevice` derive capabilities from member devices or share converter setup logic with `LightDevice`.

### `XDevice` class-level mutable defaults

- Issue: `XDevice` declares `converters: Dict[str, Converter] = None` and `hass = None` as class-level attributes. While `converters` is re-assigned in `__init__`, `hass` is a class-level attribute shared across all instances until overwritten per-instance.
- Files: `custom_components/yeelight_pro/core/device.py:83-84`
- Impact: In theory, setting `device.hass` on one instance could leak to others if not properly initialized. In practice, it is overwritten in `add_device()`, but the pattern is fragile.
- Fix approach: Move `hass` and `converters` initialization into `__init__()`.

### `XActionEntity` uses `asyncio.create_task` without HA lifecycle tracking

- Issue: `XActionEntity.async_set_state()` at line 75 calls `asyncio.create_task(self.clear_state())` directly instead of using `self.hass.async_create_task()`. This creates untracked tasks that HA cannot cancel on shutdown.
- Files: `custom_components/yeelight_pro/sensor.py:75`
- Impact: During HA shutdown, the clear_state task may run after the entity is removed, potentially causing `async_write_ha_state()` errors.
- Fix approach: Use `self.hass.async_create_task()` or store and cancel in `async_will_remove_from_hass()` (partially done but uses `cancel()` without awaiting).

### `from_node` factory uses long if/elif chain for device type mapping

- Issue: `XDevice.from_node()` uses a 20-line if/elif chain to map `DeviceType` to device classes. Adding a new device type requires modifying this method.
- Files: `custom_components/yeelight_pro/core/device.py:114-173`
- Impact: Violates open-closed principle. Each new device type requires editing the factory method.
- Fix approach: Use a `DEVICE_TYPE_MAP: Dict[int, Type[XDevice]]` registry that device classes register into, or a match statement.

### Climate `async_set_fan_mode` passes arbitrary kwargs to device

- Issue: `XClimateEntity.async_set_fan_mode()` passes the full `**kwargs` dict (from HA service call) into `device_send_props()` alongside `fan_mode`. This can forward unexpected keys to the gateway.
- Files: `custom_components/yeelight_pro/climate.py:112-115`
- Impact: Unintended gateway properties may be set if HA passes additional kwargs in future versions.
- Fix approach: Only send `{'fan_mode': fan_mode}` instead of the full kwargs dict.

### Climate `async_turn_on`/`async_turn_off` same issue with kwargs passthrough

- Issue: Same pattern as fan_mode -- `async_turn_on()` and `async_turn_off()` pass full kwargs through.
- Files: `custom_components/yeelight_pro/climate.py:117-125`
- Fix approach: Only send `{'is_on': True/False}`.

## Dependencies at Risk

## Scaling Limits

### Single TCP connection per gateway

- Current capacity: One persistent TCP connection per configured gateway.
- Limit: The gateway protocol is inherently single-connection. If message volume from many devices (100+) exceeds what a single TCP stream can handle, messages may be dropped or delayed.
- Files: `custom_components/yeelight_pro/core/gateway.py:460-501` (read loop)
- Scaling path: The 4KB read buffer with 1MB limit is reasonable. The `MSG_SPLIT` framing is simple. For very large installations, consider parallel node queries or batching topology requests.

### In-memory device/entity storage

- All devices and entities are stored in Python dicts on the gateway object. There is no persistence layer.
- Files: `custom_components/yeelight_pro/core/gateway.py:111` (`self.devices`), `custom_components/yeelight_pro/core/device.py:95` (`self.entities`)
- Impact: On HA restart, all device state must be re-fetched from the gateway via topology request. This is by design for a local-push integration but means startup time scales linearly with device count.
